SewaSetu — AI-Powered Pension Portal

An e-governance platform for old-age pension workflows built on a dual Model Context Protocol (MCP) architecture — separate Citizen and Officer MCP servers with independent JWT authorization boundaries, backed by PostgreSQL and deployed via Docker Compose.

TL;DR

  • Citizen MCP (port 8001) and Officer MCP (port 8002) expose separate tool sets with independent JWT authorization — a citizen token cannot access officer-only tools.
  • Portal (Flask/FastAPI, port 8000) is the system of record; MCP servers call the portal API for authorized data access.
  • Evaluation dashboards per MCP server; Docker Compose orchestrates all services with PostgreSQL as shared data store.

Problem

Public-welfare pension systems require strict role separation: a citizen should only access their own application data, while a block officer needs tools to list, review, and decide on pending applications. Existing monolithic approaches mix these concerns — creating both security risks and confusing user interfaces.

Approach

The Citizen MCP server (port 8001) exposes tools like check_eligibility and submit_application. It validates JWT tokens against the citizen audience — an officer token is explicitly rejected. Citizens interact through a web portal or an AI assistant making Streamable HTTP MCP calls.

The Officer MCP server (port 8002) exposes list_pension_applications, get_pension_application, and decide_pension_application — with explicit confirmation required before any state-changing decision. JWT audience is officer. A citizen token cannot access these tools.

Both MCP servers call the Portal API for authorized data access; the Portal is the single system of record backed by PostgreSQL. Docker Compose orchestrates all services; each MCP exposes its own evaluation dashboard for observability.

Security implementation details
  • JWT issuer: Portal publishes JWKS at /.well-known/jwks.json
  • Audience separation: Citizen MCP expects aud=citizen; Officer MCP expects aud=officer
  • Tool isolation: Officer-only tools are defined exclusively in officer-mcp service
  • Decision guard: decide_pension_application requires explicit confirm: true parameter — no accidental state changes
  • Evaluation dashboards: Each MCP exposes /eval-dashboard showing recent tool-call events, masked identifiers

Outcome

SewaSetu demonstrated a production-ready dual-MCP architecture where identity isolation between citizen and officer roles is enforced at the protocol level — not through application-level checks that could be bypassed.

Qualitatively: the authorization boundary held across all test scenarios — citizen tokens were rejected by the Officer MCP, officer tokens were rejected by the Citizen MCP, and decisions without confirmation flags produced no state changes.

What I learned

  • MCP's tool-call model is well-suited to e-governance: each tool maps cleanly to a workflow step with explicit inputs and audit trail.
  • JWT audience separation is architecturally cleaner than runtime role-checks — the boundary is enforced before tool execution, not inside it.
  • Evaluation dashboards are essential for demonstrating correctness in a demo context — inspectors need evidence of tool-call outcomes, not just assertion that it works.
